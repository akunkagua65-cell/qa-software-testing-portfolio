# Задание 4. Black-box тестирование приложения «Найди и иди»

## 1. Описание методологии и стратегии тестирования
В рамках данного задания разработан комплексный чек-лист для тестирования мобильного приложения «Найди и иди» по методологии **Black-box (метод черного ящика)**. Тестирование проводится исключительно на основании внешних интерфейсов, спецификаций и исправленных бизнес-требований (полученных в Задании 3), без доступа к внутреннему коду приложения.

**Использованные техники тест-дизайна:**
*   **Эквивалентное разделение (Equivalence Partitioning):** разделение входных данных (например, длины поисковой строки или уровня заряда) на классы валидных и невалидных значений.
*   **Анализ граничных значений (Boundary Value Analysis):** проверка пограничных состояний (1, 2, 3 символа в поле ввода, критический порог заряда батареи 10%).
*   **Таблица принятия решений (Decision Table):** для состояний и условий активации кнопок «Поиск» и «Построить маршрут».
*   **Диаграмма перехода состояний (State Transition):** для проверки изменения состояний кнопок при клике и изменении условий.
*   **Предугадывание ошибок (Error Guessing):** ввод спецсимволов, пустых строк, избыточного текста, имитация обрыва связи.

## 2. Использование ИИ в качестве второго аналитика для генерации черновика
Процесс разработки был разделен на 3 этапа согласно учебной методологии:
1.  **Самостоятельное проектирование:** Написание базового чек-листа на основе исправленного ТЗ.
2.  **Запрос к ИИ:** Использование нейросети для генерации альтернативного чек-листа.
3.  **Критический анализ и слияние:** Сравнение результатов, выявление слепых зон и формирование финального мастер-чек-листа.

> **Промпт для ИИ:**
> *«Ты — ведущий QA Automation / Manual инженер. На основе исправленного ТЗ мобильного приложения "Найди и иди" (блоки SC21-01 — SC21-06) составь подробный чек-лист проверок по методологии Black-box. Раздели проверки по модулям: Поле ввода, Выпадающий список, Кнопка Поиск, Кнопка Построить маршрут, Карта, Общие системные сценарии. Включи позитивные, негативные и граничные сценарии. Оформи в виде чек-листа Markdown.»*

### Результаты сравнения:
*   **Что было лучше в моем варианте:** Более глубокая детализация UI-элементов, конкретные шестнадцатеричные коды цветов кликабельных кнопок (`#ffffff` и `#586d73`), четкие правила для UX при удалении текста плейсхолдера, а также детальные сценарии на сброс фильтров при изменении поисковых параметров.
*   **Что было лучше в варианте ИИ:** ИИ предложил отличные негативные сценарии на прерывание операций (например, входящий звонок во время рендеринга маршрута, сворачивание приложения при низком заряде аккумулятора) и точечные проверки на производительность при отображении более 100 флажков на карте.
*   **Итог интеграции:** Все сильные стороны ИИ-черновика (обработка прерываний, нагрузка на отрисовку) были успешно объединены с моей детальной UI/UX-базой в финальную версию ниже.

## 3. Финальный объединенный чек-лист

### 📌 Модуль: SC21-01 — Поле ввода названия магазина
- [ ] **Валидация ввода (Позитивные сценарии):**
  - [ ] Ввод корректного названия на кириллице (например, *"Аптека Живика"*) -> Текст отображается корректно.
  - [ ] Ввод корректного названия на латинице (например, *"Magnit"*) -> Текст отображается корректно.
  - [ ] Ввод чисел и дефисов (например, *"Магазин 24-Семь"*) -> Текст отображается корректно.
- [ ] **Анализ граничных значений (Длина строки):**
  - [ ] Ввод 1 символа -> Кнопка «Поиск» остается неактивной, валидация не пройдена.
  - [ ] Ввод 2 символов (Нижняя граница) -> Кнопка «Поиск» активируется (при условии выбора типа магазина или как самостоятельный параметр).
  - [ ] Ввод 3 символов -> Кнопка «Поиск» активна.
  - [ ] Ввод строки экстремальной длины (1000+ символов) -> Приложение не зависает, текст обрезается по лимиту базы данных или выдается валидационная ошибка.
- [ ] **Негативные сценарии и безопасность:**
  - [ ] Ввод только пробелов (2 пробела) -> Кнопка «Поиск» неактивн
а, пробелы автоматически триммируются.
  - [ ] Попытка SQL/XSS инъекции (например, `<script>`, `SELECT *`) -> Символы экранируются, приложение обрабатывает строку как чистый текст, уязвимостей нет.
- [ ] **Проверка поведения Плейсхолдера:**
  - [ ] Проверка отображения дефолтного плейсхолдера после загрузки страницы.
  - [ ] Ввод 1-го символа -> Плейсхолдер мгновенно исчезает.
  - [ ] Полное удаление текста -> Плейсхолдер мгновенно возвращается в исходное состояние.
- [ ] **История поиска:**
  - [ ] Сохранение последней успешной строки поиска после закрытия/открытия сессии приложения.
  - [ ] Проверка автозаполнения/саггестов при вводе первых букв из истории.

### 📌 Модуль: SC21-02 — Поле выбора типа магазина
- [ ] **Проверка структуры списка:**
  - [ ] Нажатие на выпадающее меню -> Открывается список ровно с 3 элементами: *«Продуктовые магазины»*, *«Магазины стройматериалов»*, *«Аптеки»*.
  - [ ] Элементы расположены в строго заданном ТЗ порядке, ручной ввод в поле полностью заблокирован.
- [ ] **Управление состоянием:**
  - [ ] Выбор любого элемента списка -> Меню закрывается, выбранное значение фиксируется в поле.
  - [ ] Повторное открытие списка и смена выбора -> Значение успешно обновляется в UI.
- [ ] **Отображение плейсхолдера:**
  - [ ] До выбора элемента отображается текст *«Выберите тип магазина»* (проверка серого цвета согласно UI-киту).
  - [ ] После выбора элемента плейсхолдер заменяется на выбранный текст стандартного начертания.

### 📌 Модуль: SC21-03 — Кнопка «Поиск»
- [ ] **Матрица состояний кнопки (Зависимость от полей):**
  - [ ] Оба поля пустые -> Кнопка имеет статус `disabled` (визуально неактивна, клик заблокирован).
  - [ ] Заполнено только «Название» (>=2 симв.), «Тип» пуст -> Кнопка переходит в статус `active`.
  - [ ] «Название» пустое, выбран «Тип магазина» -> Кнопка переходит в статус `active`.
  - [ ] Заполнены оба параметра -> Кнопка переходит в статус `active`.
- [ ] **Обработка клика и результаты:**
  - [ ] Клик по неактивной кнопке -> Действие не вызывается, состояние интерфейса не меняется.
  - [ ] Клик по активной кнопке -> Выполняется запрос, отображается лоадер, результаты выводятся в виде флажков на карте.
- [ ] **Отображение результатов на карте:**
  - [ ] Флажки (иконки пинов) размещаются в точных географических координатах найденных магазинов.
  - [ ] Каждый флажок содержит корректную подпись с названием магазина.
  - [ ] При изменении параметров поиска старые флажки полностью очищаются, наносятся новые.

### 📌 Модуль: SC21-04 — Кнопка «Построить маршрут»
- [ ] **Позитивные сценарии активации:**
  - [ ] Сценарий 1: Найден магазин по названию + пользователь тапнул на его флаг на карте -> Кнопка становится активной.
  - [ ] Сценарий 2: Выбран только тип магазина из списка -> Кнопка становится активной (расчет до ближайшего).
- [ ] **Проверка визуализации и стилей (UI/UX):**
  - [ ] Дефолтное состояние: цвет фона `#ffffff` (белый), иконка изогнутой стрелки, текст *«Построить маршрут»*.
  - [ ] Клик по активной кнопке -> Цвет фона мгновенно меняется на серый (`#586d73`), текст меняется на *«Отменить маршрут»*.
  - [ ] Повторный клик (отмена) -> Маршрут удаляется, кнопка возвращается в исходный белый цвет и текст *«Построить маршрут»*.
- [ ] **Негативные сценарии:**
  - [ ] Кнопка нажата при отсутствии интернета -> Отображается корректный алерт о потере сети, маршрут не строится, приложение не падает.
  - [ ] Выбран тип магазина, но в радиусе доступности нет таких магазинов -> Кнопка активна, но при клике выдается сообщение *"Магазины данного типа не найдены"*.

### 📌 Модуль: SC21-06 — Общие системные сценарии
- [ ] **Сохранение состояния сессии (Жизненный цикл):**
