# Задание 1. Классификация тестирования



1.  **Модуль переводов** — часть приложения, которая умеет переводить деньги (пока без связи с реальным банком)
2.  **Макеты экранов** — картинки того, как должно выглядеть приложение
3.  **Первая версия приложения** — готовая программа для тестирования внутри компании


## Таблица категорий тестирования

| По стадии проведения процесса тестирования | По знанию устройства системы | По направленности тестового сценария | По выполнению кода |
|---------------------------------------------|-------------------------------|---------------------------------------|---------------------|
| **Альфа-тестирование:** проверка макета интерфейса (п. 2) силами дизайнеров и продакт-менеджеров на удобство и логичность переходов. | **Черный ящик:** функциональное тестирование модуля перевода средств: проверка корректности списания и зачисления при разных валидных и невалидных суммах (без знания внутренней реализации). | **Позитивное тестирование:** успешный перевод с одного счёта на другой при корректных реквизитах и достаточном балансе. | **Ручное тестирование:** проверка макета интерфейса (п.2) на соответствие дизайн-макетам и удобство использования |
| **Дымовое тестирование (Smoke):** после сборки приложения проверить, что основные экраны открываются, модуль перевода запускается без критических ошибок. | **Серый ящик:** тестирование обработки ошибок в модуле перевода: проверка сообщений пользователю при недостатке средств, с имитацией ответов от заглушки банковского шлюза. | **Негативное тестирование:** попытка перевода суммы, превышающей доступный баланс, и проверка соответствующего сообщения об ошибке. | **Динамическое тестирование:** запуск unit-тестов для функций расчёта комиссии (если есть) в модуле перевода. |
| **Приёмочное тестирование (на уровне макета):** проверка заказчиком/стейкхолдерами соответствия макета интерфейса бизнес-требованиям и дизайн-системе. | **Белый ящик:** тестирование покрытия условий в коде модуля перевода (например, проверка всех ветвей логики при валидации введённой суммы). | **Тестирование на отказ и восстановление:** имитация прерывания процесса перевода (сворачивание приложения, отключение сети) и проверка целостности данных после возврата. | **Тестирование сборки:** проверка корректности компиляции и сборки приложения для разных типов устройств и версий ОС. |
| **Интеграционное тестирование:** проверка взаимодействия модуля перевода с другими модулями приложения (например, с модулем уведомлений об успешной операции). | **Смешанное тестирование:** проверка безопасности передачи данных в модуле перевода: анализ кода на наличие уязвимостей (белый ящик) и попытки внедрения тестовых атак через интерфейс (чёрный ящик). | **Нагрузочное тестирование (на уровне модуля):** проверка производительности модуля перевода при одновременном выполнении нескольких запросов на перевод. | **Ручное и автоматизированное тестирование:** комбинация тестов для проверки удобства интерфейса (п.2) и функциональности приложения |
| **Регрессионное тестирование:** после внесения изменений в интерфейс на основе альфа-тестирования проверить, что ранее работавший функционал перевода не сломался. | **Экспертное тестирование:** анализ архитектуры модуля перевода специалистом по безопасности на предмет потенциальных уязвимостей при интеграции с реальным банковским шлюзом. | **Юзабилити-тестирование (на макете):** оценка удобства и интуитивности экрана перевода средств внутренними сотрудниками. | **Тестирование производительности кода:** профилирование модуля перевода для выявления узких мест в алгоритмах обработки операций. |
