# Анализ архитектуры баз данных на примере Яндекс Маркета

## 1. Теоретический блок: Сравнение типов БД

### Реляционные (SQL) vs Нереляционные (NoSQL)

| Характеристика | Реляционные (SQL) | Нереляционные (NoSQL) |
| :--- | :--- | :--- |
| Принцип хранения | Строгие таблицы с фиксированными колонками и связями (первичные/внешние ключи). | Документы (JSON/BSON), пары ключ-значение, колоночные или графовые структуры. |
| Схема данных | Фиксированная (Schema-on-write). Требует проектирования заранее. | Гибкая (Schema-on-read). Поля могут различаться у разных записей. |
| Масштабирование | Вертикальное (увеличение мощности сервера). Горизонтальное (шардирование) сложно. | Горизонтальное (легкое добавление серверов в кластер). |
| Целостность (ACID) | Максимальная надежность. Поддержка транзакций (Commit/Rollback). | Часто жертвует строгостью в пользу скорости (CAP-теорема). |
| Примеры СУБД | PostgreSQL, MySQL, Oracle, MS SQL Server. | MongoDB, Redis, Cassandra, ElasticSearch. |

Плюсы SQL:
- Надежность: Идеально для финансовых операций, где важна каждая копейка и жесткая связь (например, заказ → платеж → чек).
- Сложные запросы: Позволяют легко соединять таблицы через JOIN для аналитики.

Минусы SQL:
- Сложность изменений: Изменение схемы (ALTER TABLE) на больших объемах данных может потребовать простоя сервиса.
- Горизонтальное масштабирование: Требует ручного шардирования или специальных решений.

Плюсы NoSQL:
- Скорость: Огромная скорость записи и чтения по ключу.
- Гибкость: Легко хранить разные наборы полей (например, характеристики для разных категорий товаров).
- Масштабируемость: Легко добавлять новые серверы в кластер.

Минусы NoSQL:
- Слабая связность: Обычно не поддерживают JOIN, что ведет к дублированию данных.
- Ограничения транзакций: Сложно гарантировать атомарность при обновлении данных сразу в нескольких документах.

### Сравнение СУБД одного типа: PostgreSQL vs MySQL

Несмотря на то, что обе системы — реляционные, у них разные задачи:
- MySQL: Простая, надежная и очень быстрая на операциях чтения (SELECT). Часто используется в веб-разработке для блогов или интернет-магазинов с простой структурой.
- PostgreSQL: Более продвинутая ("умная") база. Поддерживает сложные типы данных (JSONB, массивы), лучше работает со сложными запросами и аналитикой, а также имеет встроенные механизмы для предотвращения повреждения данных. Хорошо подходит для систем с высокими требованиями к целостности.

## 2. Гипотеза об архитектуре Яндекс Маркета

Гипотеза: Яндекс Маркет использует гибридный подход с собственной распределенной СУБД YDB в качестве ядра.

Аргументация: Яндекс Маркет — это маркетплейс с десятками миллионов товаров и миллиардами поисковых запросов в сутки. Для такого масштаба невозможно обойтись одной БД. Финансовая часть (заказы, платежи) требует надежности и ACID-транзакций (SQL/реляционный подход). Каталог товаров с миллионами разных характеристик требует гибкости NoSQL. А поиск и выдача — скорости работы в оперативной памяти. Яндекс разработал собственную распределенную СУБД YDB, которая сочетает в себе преимущества SQL и NoSQL, обеспечивая масштабируемость, отказоустойчивость и строгую согласованность данных.

## 3. Разбор ключевых функций сервиса

### Функция 1: Обработка заказов и транзакций
- Используемые данные: Сумма оплаты, ID пользователя, статус платежа, чеки, данные доставки, информация о продавце.
- Подходящий тип БД: Реляционная (SQL) / YDB (реляционный режим)
- Почему: Здесь важна транзакционность и целостность данных (ACID). Если в момент оплаты произойдет сбой, база должна либо полностью завершить операцию, либо полностью её отменить, чтобы деньги не "зависли" в воздухе. YDB обеспечивает строгую согласованность и ACID-транзакции.

### Функция 2: Каталог товаров и фильтры
- Используемые данные: Технические характеристики (для электроники — вольты, для одежды — состав ткани, размеры), описания, цены, остатки на складе.
- Подходящий тип БД: Нереляционная (документо-ориентированная / YDB в режиме документов)
- Почему: У разных категорий товаров — разные свойства. В NoSQL можно хранить их как JSON-документы. Это позволяет быстро добавлять новые категории товаров без изменения структуры всей базы. В YDB данные хранятся в распределенных "таблетках" (tablets), которые автоматически шардируются при росте нагрузки.

### Функция 3: Поиск товаров и выдача результатов
- Используемые данные: Поисковый индекс (текст, категории, бренды), сниппеты (описания, картинки), релевантность.
- Подходящий тип БД: Специализированная поисковая (In-memory / Key-Value)
- Почему: Поисковый индекс должен полностью помещаться в оперативной памяти для быстрого ответа. В Яндекс Маркете индекс разделен на 8 шардов (частей) для горизонтального масштабирования. Также используется отдельный сниппетный сервер с Key-Value базой данных для хранения статической информации о товарах.

### Функция 4: Избранное и списки пользователя
- Используемые данные: ID пользователя, список ID товаров, названия списков, даты добавления.
- Подходящий тип БД: Нереляционная (документо-ориентированная / Key-Value)
- Почему: Эти данные имеют простую структуру (связь пользователь → список товаров), но требуют быстрого доступа и гибкости при добавлении новых типов списков. NoSQL база легко масштабируется при росте количества пользователей.

## 4. Идеи для тест-кейсов (Проверка БД)

### Тест-кейс №1: Проверка целостности при оплате (ACID)
- Действие: Имитировать потерю связи сервера с базой данных в момент списания средств за заказ.
- Что проверяем: Что в БД не произошло частичного обновления (деньги списались со счета пользователя, а статус заказа остался "не оплачен" или заказ создался без списания). Запись должна либо обновиться целиком, либо не измениться вовсе. YDB должна гарантировать атомарность транзакции.

### Тест-кейс №2: Проверка гибкости каталога (NoSQL)
- Действие: Попробовать загрузить через партнерский интерфейс товар с новым полем (например, "Максимальная частота процессора" для категории "Смартфоны", где такого поля раньше не было).
- Что проверяем: Как база данных обрабатывает нетипичное поле. Она не должна выдавать ошибку, а должна просто сохранить это свойство как новый атрибут документа. YDB, работая с JSON-подобными данными, должна это поддерживать.

### Тест-кейс №3: Проверка отказоустойчивости поиска (In-memory / Шардирование)
- Действие: В тестовой среде отключить один из 8 серверов, содержащих шард поискового индекса.
- Что проверяем: Должна ли база данных продолжать отвечать на поисковые запросы? Если да, то как это влияет на полноту выдачи (отсутствует один шард из 8)? Как быстро система восстановит индекс на резервном сервере? В реальной архитектуре Яндекс Маркета балансеры автоматически перенаправляют запросы на работающие серверы, а health-check отслеживает состояние каждого сервера.

## 5. Рефлексия (Реальная архитектура)

Результат поиска после выполнения задания:

Мои предположения в целом совпали с реальной архитектурой, но оказались даже интереснее.

Что я узнала из открытых источников:

1. YDB — собственная разработка Яндекса: В основе Яндекс Маркета (а также Такси, Алисы и еще 500 проектов) лежит распределенная СУБД YDB (Yandex Database). Она была открыта в 2022 году под лицензией Apache 2.0.

2. Гибридная природа YDB: YDB — это Distributed SQL Database, которая сочетает преимущества реляционных (ACID-транзакции, строгая согласованность) и нереляционных (горизонтальное масштабирование, отказоустойчивость) баз данных. Это подтверждает мою гипотезу о гибридном подходе.

3. Масштабы: YDB обрабатывает миллионы запросов в секунду (RPS), хранит петабайты данных и работает в трех зонах доступности.

4. Архитектура "таблеток" (Tablets): Данные в YDB разделены на компоненты "таблетки", которые автоматически шардируются при росте нагрузки. Если таблетка не справляется, она разделяется на две, и они начинают работать параллельно.

5. Поисковая инфраструктура отдельно: Поиск в Маркете работает на собственной инфраструктуре — поисковый индекс разделен на 8 шардов и хранится в оперативной памяти серверов, а для сниппетов (описаний) используется отдельная Key-Value база данных. Для быстрой работы с API и кэширования также используются ElasticSearch, PostgreSQL и Redis.

6. HTAP-подход: Яндекс развивает YDB как гибридную базу данных, поддерживающую одновременно OLTP-нагрузки (транзакции) и OLAP-нагрузки (аналитику).

Вывод: Моя гипотеза подтвердилась — Яндекс Маркет действительно использует гибридный подход, но с уникальной собственной разработкой YDB, которая закрывает потребности и в надежных транзакциях, и в масштабируемом хранении данных, и в отказоустойчивости.
