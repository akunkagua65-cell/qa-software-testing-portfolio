# Анализ клиент-серверной архитектуры и отказоустойчивости

## 1. Трехзвенная и многозвенная архитектура

В современной веб-разработке доминируют многозвенные (n-tier) архитектуры, которые эволюционировали из классической двухзвенной модели «клиент-сервер». Основная цель разделения на звенья — снижение связанности компонентов и повышение масштабируемости.

### Трехзвенная архитектура
* Клиентское звено (Presentation Tier): Отвечает за интерфейс пользователя и взаимодействие с ним (веб-браузер, мобильное приложение).
* Звено бизнес-логики (Application Tier / Middleware): Сердце приложения. Здесь обрабатываются запросы, применяются правила бизнеса (например, расчет скидки, проверка прав доступа).
* Звено данных (Data Tier): Отвечает за хранение и управление данными (СУБД, файловые хранилища).

### Многозвенная архитектура
Представляет собой дальнейшее развитие трехзвенной модели. Промежуточное звено (*Application Tier*) дробится на множество микросервисов, добавляются новые уровни: 
* Кэширующие серверы (*Redis / Memcached*)
* Очереди сообщений (*RabbitMQ / Kafka*)
* Балансировщики нагрузки
* CDN и API-шлюзы

Это позволяет гибко масштабировать отдельные части системы независимо друг от друга.

## 2. Анализ реального приложения: Интернет-магазин «Wildberries»

Для анализа выбрана архитектура типичного крупного маркетплейса. Ниже представлены ключевые компоненты схемы взаимодействия.

### Ключевые компоненты и их назначение

| № | Компонент | Назначение |
| :-: | :--- | :--- |
| 1 | Балансировщик нагрузки<br>*(Load Balancer)* | Распределяет входящий трафик между несколькими фронтенд-серверами. Обеспечивает отказоустойчивость (если один сервер падает, трафик идет на другой) и высокую доступность. |
| 2 | API-шлюз<br> *(API Gateway)* | Единая точка входа для всех запросов от клиентов. Маршрутизирует запросы к нужным микросервисам, агрегирует ответы, занимается аутентификацией запросов и лимитированием (*rate limiting*). |
| 3 | Сервис Корзины<br> *(Микросервис)* | Управляет состоянием корзины пользователя. Отвечает за добавление/удаление товаров, хранение выбранных позиций, часто используя быстрые in-memory базы данных (*Redis*) для высокой скорости работы. |
| 4 | База данных заказов<br> *(Data Tier)* | Отвечает за надежное и консистентное хранение данных о размещенных заказах. Обычно это реляционная СУБД (*PostgreSQL, MySQL*), обеспечивающая транзакционность (*ACID*), чтобы не потерять деньги и товары. |

## 4. Сравнение стратегий резервирования: «Горячий» vs «Холодный» резерв

| Критерий | «Горячий» резерв<br>*(Active-Active / Hot Standby)* | «Холодный» резерв<br>*(Cold Standby)* |
| :--- | :--- | :--- |
| Готовность | Резервный компонент постоянно работает (включен) и принимает трафик или полностью синхронизирован. | Резервный компонент выключен или не настроен. |
| Синхронизация данных | Постоянная синхронизация в реальном времени или близком к реальному (синхронная или асинхронная репликация). | Данные либо не синхронизированы, либо синхронизируются по расписанию (например, раз в сутки). |
| Время переключения (RTO) | Секунды или минуты. Переключение происходит автоматически или по нажатию одной кнопки. | Часы или даже дни. Требуется развернуть софт, восстановить данные с бэкапа, применить конфигурации. |
| Стоимость | Высокая. Требуется покупка и обслуживание дублирующего оборудования и каналов связи (лицензии, электричество, администрирование). | Низкая. Требуется только носитель с бэкапом (лента, диск) или аренда "холодного" места в ЦОД. |
| Плюсы | Минимальное время простоя (*Downtime*). Почти незаметно для пользователя. | Дешевизна и простота организации. Защита от "человеческого фактора" (случайного удаления данных — можно откатиться на вчерашний бэкап). |
| Минусы | Не защищает от логических ошибок (если данные испорчены на основном сервере, они мгновенно испортятся и на горячем резерве). | Длительный простой. Потеря данных с момента последнего бэкапа (*RPO может составлять сутки*). |

## 5. Сценарий теста отказоустойчивости

* Компонент: База данных заказов с «горячим» резервом.
* Контекст: У нас есть мастер-сервер БД заказов (*Primary*) и реплика (*Replica*), работающая в режиме горячего резерва (*Hot Standby*). Настроена асинхронная репликация. Система должна автоматически повысить реплику до мастера (*auto-failover*) при отказе основного узла.
* Название теста: Проверка автоматического переключения (*Failover*) при отказе Master-ноды базы данных.

### Предусловия
1. Развернута тестовая среда, аналогичная production.
2. Сгенерирован фоновый трафик (инструментом типа *JMeter*), имитирующий оформление заказов (10 заказов в секунду).
3. Настроен мониторинг (*Prometheus / Grafana / Zabbix*).
4. Зафиксировано текущее состояние (Master — Server A, Replica — Server B).

### Шаги сценария

| № | Действие | Ожидаемый результат |
| :-: | :--- | :--- |
| 1 | Запустить сбор метрик и логирование. | Метрики записываются, логи поступают в систему сбора логов. |
| 2 | Искусственно остановить процесс СУБД на Master-сервере (Server A) или отключить его сетевой интерфейс. | Симуляция аварии основного узла. |
| 3 | Отследить срабатывание системы мониторинга (*alert*). | Система мониторинга фиксирует недоступность Master-сервера и отправляет оповещение. |
| 4 | Проверить, что система управления кластером автоматически повысила статус Server B (Replica) до нового Master. | Статус Server B изменился с "replica" на "master". |
| 5 | Проверить, что приложение (API-шлюз и сервис заказов) перенаправило поток записи на новый мастер (Server B). | Запросы на запись данных больше не направляются на недоступный Server A. |
| 6 | Убедиться, что новые заказы успешно создаются и записываются в БД. | Новые заказы появляются в БД на новом мастере (Server B), пользователи могут оформлять заказы. |
| 7 | *(Опционально)* Восстановить старый мастер и проверить, что он вернулся в строй как реплика. | Server A после перезапуска синхронизируется с новым мастером и работает как реплика, не пытаясь стать мастером (отсутствие *split-brain*). |

### Отслеживаемые показатели

* RTO (Recovery Time Objective): Время от момента остановки Master до момента начала успешной записи в новый Master. 
  * *Целевое значение:* Менее 60 секунд
* RPO (Recovery Point Objective): Количество потерянных заказов/данных. Сравнить последнюю запись в старом мастере и первую в новом.
  * *Целевое значение:* Минимизация потерь *(для асинхронной репликации возможны незначительные потери)*
* Успешность ответов (HTTP 200): График количества успешных оформлений заказов. Во время переключения ожидается небольшой всплеск ошибок (503/504), но после *failover*'а они должны упасть до нуля.
* *Целевое значение:* Ошибки не более 5% в момент переключения, затем 0%
* Время ответа API: Время ответа API сервиса заказов. Не должно критически вырасти после переключения на резервный узел.
  * *Целевое значение:* Увеличение не более чем на 20% от baseline
* Состояние кластера: Подтверждение, что старый мастер (после перезапуска) вернулся в строй уже в роли реплики.
  * *Целевое значение:* Split-brain не допущен, кластер в состоянии "green"
